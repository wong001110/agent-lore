# Agent Lore

**Cross-project engineering evidence, guardrails, observability, and adaptive calibration for coding agents.**

Agent Lore is designed to remain useful as foundation models and coding harnesses change. It records what happened, what was verified/accepted, what historical evidence may help, and which capability boundaries must hold—without trying to replace the current model's reasoning with an accumulated SOP.

> Status: **Integrated Alpha / v0.9.0-alpha**. Scoped Evidence Capsules, pull-based memory modes, model/harness routing telemetry, acceptance/rework lineage, TaskShape/EvidencePlan routing, proportional verification/security, optional execution ledgers, and lazy runtime artifacts are implemented. Project-context auto-discovery and richer per-node runtime routing remain future host/runtime work.

## Core principles

```text
Constrain capability, not cognition.
Observe execution, do not script it.
Expose history on demand, do not preload it.
Respect project structure, do not replace it.

Past experience is evidence, not truth.
Execution success is not final success.
Functional success does not prove security.
More agents/tests/attacks/commits are not automatically better.
Project state belongs to the project, not Agent Lore.
```

Agent Lore is a **sidecar control + evidence plane**, not a universal coding runtime or a growing prompt-level rulebook.

See [`references/SIDECAR.md`](references/SIDECAR.md).

## Model freedom

Policies use four strengths:

```text
hard
strong-default
advisory
experimental
```

Hard policy is reserved for independently justified permission/safety/budget/irreversible-action boundaries. Wherever technically possible, hard capability limits should be enforced by the host harness/tool layer rather than repeated as prompt instructions.

Historical experience does **not** automatically become policy. Current user requirements, project instructions/ADRs, source/runtime evidence, dependency versions, deterministic verification, and current-model judgment outrank old experience.

See [`references/POLICY.md`](references/POLICY.md).

## Project structure stays project-owned

Agent Lore is cross-project, but it does not require every repository to adopt the same folders.

A project may already have:

```text
AGENTS.md
README/docs/wiki
ADRs/specs
source/tests/CI
security docs
```

or a completely different structure. Agent Lore treats these as semantic project-context roles rather than imposing a directory convention.

Normal startup:

```text
current task
  -> discover/read project-owned instructions/current state
  -> inspect affected source/tests/contracts
  -> current model forms a plan
  -> optionally retrieve scoped historical evidence
  -> work + verify
```

A future/host integration may remember local semantic mappings under `~/.agent-lore/projects/` without modifying the repository. An optional version-controlled `.agent-lore.json` may be supported for teams that explicitly want it; it is not required.

See [`references/PROJECT_CONTEXT.md`](references/PROJECT_CONTEXT.md).

## Pull-based historical memory

A new or stronger model should not pay a mandatory token/attention tax for old agents' reasoning.

Memory modes:

```text
off        -> no historical evidence enters context
guardrail  -> observations/failures/invariants only; old procedures hidden
rescue     -> reveal relevant historical cases/remedies after difficulty/failure
proactive  -> deliberate historical reveal for high-risk/explicit analysis
```

Recommendations default to historical memory **off**. Explicit `retrieve` defaults to `guardrail`.

Historical memory is scoped:

```text
task | module | project | stack | global
```

and bounded by an approximate token budget rather than assuming a large context window should be filled.

### Evidence Capsule

New reusable knowledge can record:

```text
observation
invariant
root cause + status
applicability
what is not proven
experience/failure family
historical solution + solution status
accepted/verified evidence lineage
```

The durable asset is the failure space, invariant, applicability, and evidence. A historical solution is one variant, not an instruction to future models.

Avoid summary-of-summary chains. Structured run/evidence state is canonical; cards/reports/summaries are derived and may be regenerated by future models.

See [`references/MEMORY.md`](references/MEMORY.md).

## Learned Agent Skills are retired

v0.9 stops promoting/materializing historical experience into generated Agent `SKILL.md` files.

Why:

- procedure-shaped artifacts are more likely to anchor future models
- scoped Experience/Pattern evidence already preserves useful history
- newer models should be free to find better implementations while still seeing verified failure/invariant evidence when useful

Existing legacy `kind=skill` rows/files remain readable/portable for backward compatibility, but are excluded from normal retrieval and cannot be newly created.

The intended lifecycle is now:

```text
run observation
  -> verification
  -> acceptance/rework
  -> reusable evidence?
       ├─ no -> statistics only
       └─ yes -> scoped experience
                  -> reusable pattern when justified
```

See [`references/LIFECYCLE.md`](references/LIFECYCLE.md).

## Adaptive execution

Single-agent execution remains a strong default, not because future models are assumed weak but because coordination has cost.

TaskShape may describe:

```text
objective
workstreams + dependencies
read/write/contract scopes
risk/uncertainty
integration points
verification/security surfaces
```

Modern execution output separates:

```text
Coordination: single | manager-worker | hierarchical | peer-handoff
Schedule:     serial | parallel | hybrid
Depth:        0 | 1 | 2+
```

The current model/host decides whether delegation is useful. Agent Lore validates host-supplied dependency/scope structure, applies hard budget ceilings, records outcomes, and can learn task-conditioned delegation lift. It should not dictate fixed frontend/backend/etc. agent classes.

See [`references/ROUTING.md`](references/ROUTING.md) and [`references/EXECUTION.md`](references/EXECUTION.md).

## Proportional verification

Verification should prove claims rather than maximize test count.

```text
change impact + risk + novelty + blast radius
                 ↓
              EvidencePlan
                 ↓
       cheap/high-information checks first
                 ↓
        enough evidence? -> stop/escalate
```

V0-V4 are depth signals, not recipes. Expensive E2E/regression/mutation/red-team work normally belongs at meaningful integration/feature/release checkpoints when the risk warrants it.

Security depth remains adaptive:

```text
none | smoke | focused | deep | adversarial
```

See [`references/EXECUTION.md`](references/EXECUTION.md) and [`references/SECURITY.md`](references/SECURITY.md).

## Security

Security is expressed as durable assets/trust boundaries/allowed flows/invariants rather than model-specific attack instructions.

```text
assets
  -> trust boundaries
  -> allowed flows
  -> invariants
  -> applicable attacks
  -> synthetic canaries / isolated verification
```

A stronger future model may run deeper authorized red-team work, but the invariant and environment authorization remain stable. Attack simulation is limited to local/test/sandbox/ephemeral or explicitly authorized systems.

## Acceptance-aware continual learning

Agent Lore separates:

```text
execution outcome
      ↓
verification status
      ↓
acceptance / rework / rejection
```

A passing implementation sent back for rework is negative evidence for first-pass quality.

Negative feedback puts linked knowledge on revalidation hold. Historical evidence remains inspectable so it can explain context boundaries and failure modes rather than being silently deleted.

## New model onboarding

A new model should normally require calibration, not an Agent Lore redesign.

Register the model/harness configuration, then observe task-conditioned:

```text
acceptance / first-pass acceptance
quality
cost / wall time / retries
verification outcomes
delegation/challenge usefulness
memory-on vs memory-off lift when evaluated
```

A previous model's memory/delegation preference is not automatically inherited by the new model.

Conceptually:

```text
Memory Lift = performance(memory-assisted) - model-only baseline
```

Negative/irrelevant memory lift should narrow or disable memory for that model/task context.

## Actual execution ledger and reports

A host may attach the agents it actually used after a run:

```bash
python scripts/agent_lore.py agents record <run-id> --manifest-json @agents.json
python scripts/agent_lore.py agents show <run-id>
```

This is observational telemetry, not a spawn plan. Model/harness/specialization/cost/timing metadata are optional and missing telemetry is explicit.

Reports are derived from the SQLite store:

```bash
python scripts/agent_lore.py report --format markdown
python scripts/agent_lore.py report --format html
```

The agent does not need to stop work to write a prose report if the harness can record structured events/outcomes automatically.

## Runtime layout

Fresh install:

```text
~/.agent-lore/
└─ agent-lore.db
```

Derived/operational directories are lazy-created only when used:

```text
reports/   generated human-readable reports
exports/   default portable exports
archive/   import safety backups
```

Old `knowledge/` files may still exist on upgraded installations and are preserved in portable exports/imports for backward compatibility. v0.9 does not create new learned-skill files. Empty `traces/` and `knowledge/skills/` placeholder directories are no longer created.

## Start

```bash
python scripts/agent_lore.py init
python scripts/agent_lore.py policy show
python scripts/agent_lore.py record --help
python scripts/agent_lore.py retrieve --help
python scripts/agent_lore.py recommend --help
python scripts/agent_lore.py agents --help
python scripts/agent_lore.py report --help
```

Fresh installs start in `observe`. Historical memory for routing/recommendation defaults to `off`; explicitly calling `retrieve` defaults to `guardrail`.

## Runtime boundary

The host harness owns process/agent spawning, provider calls, filesystem/tools, sandboxing, tests, Git, project-context discovery, and deterministic enforcement it can implement.

Agent Lore stores policy, structured evidence, scoped historical cases/patterns, model/harness observations, routing decisions, rework lineage, and reports without becoming the agent's brain.
